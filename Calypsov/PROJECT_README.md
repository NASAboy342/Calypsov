# Backend Project Doc (Calypsov)

Maintained by the `back-end-enhance` skill. Read this before planning any backend change; update the Feature log after implementing one. This is a living architecture/convention doc, separate from `ReadMe.md` (which only covers build/run setup).

## Stack
- .NET 8, C#, `OutputType: Exe` — this runs as a native apphost (`bin/Debug/net8.0/Calypsov`), not `dotnet Calypsov.dll`.
- Photino.NET + Photino.NET.Server — hosts an ASP.NET minimal-API backend and a native OS window in one process.
- Newtonsoft.Json for settings persistence (`JsonConvert`); minimal-API results elsewhere use `Results.*`.
- Two run modes wired in `Program.cs` via `Program.IsDebugMode` (`#if DEBUG`):
  - Debug: window loads `http://localhost:5173` (the Vite dev server — see the `run-test` skill).
  - Release: window loads the built `wwwroot` bundle (embedded via `Resources/wwwroot`), with a cache-busting query string on load.

## Structure
- `Program.cs` — composition root. Creates the Photino static file server, builds a `ServiceCollection`/`ServiceProvider` to register and resolve services (see **Dependency injection** below), calls each feature's `Map<Feature>Endpoints(...)` extension method, then creates and shows the `PhotinoWindow`.
- `Api/` — one static class per feature (e.g. `EncryptionEndpoints.cs`, `DialogEndpoints.cs`). Each exposes a single `Map<Feature>Endpoints(this WebApplication app, ...)` extension method that groups its routes under `/api/<feature>` via `app.MapGroup(...)`.
- `Services/` — one interface per feature (`I<Feature>Service`) plus one or more implementations (e.g. `StorageEncryptionSettingsService` persists to a JSON file under the OS app-data folder; `MemoryEncryptionSettingsService` is an in-memory stand-in). `Program.cs` is the only place that decides which implementation is live — swapping implementations never touches the API surface. Services can depend on other services' interfaces this same way — `StorageEncryptionSettingsService` now also takes an `IBrowserProfileService` (see Feature log) — and the DI container resolves the whole graph automatically; nothing in `Program.cs` had to change to wire that up.
- `Repositories/` — `ISettingRepository`/`SettingRepository`: shared by every storage-backed service (currently `StorageEncryptionSettingsService`, `StorageBrowserProfileService`) to read/write a JSON settings file and to resolve the app-data folder, so each service only names its own file (`Load<T>("x.json")`/`Save("x.json", data)`) instead of re-resolving where "the app's folder" is. One instance is constructed in `Program.cs` and passed into every service that needs it (constructor injection).
- `Models/` — plain C# records/classes: response DTOs (`EncryptionStatusResponse`, `PickPathsResponse`, `ErrorResponse`), request DTOs (`AddTargetRequest`), domain types (`EncryptionTarget`, `AppSetting`, `EnumTargetCategory` + its JSON converter).
- `Helpers/` — small stateless utilities used by services (e.g. `Zip.cs` zips/unzips target folders and files).

## Conventions
- **Endpoint pattern**: `app.MapGroup("/api/<feature>")`, then `MapGet/MapPost/MapDelete` with lambda bodies. Bodies that can fail are wrapped in a local `Try(Func<IResult> body)` helper (see `EncryptionEndpoints.cs`), which turns `ArgumentException` → 400, `InvalidOperationException` → 409, anything else → 500, all as a JSON `ErrorResponse { message }`. Keep new endpoint files consistent with this — the frontend's `httpClient.requestJson` reads `body.message` on any non-2xx response, so an endpoint that doesn't follow this shape breaks that error handling.
- **Service pattern**: define the interface first, with XML doc comments explaining what each thrown exception means (since `Try` maps them to status codes). Put implementation(s) in `Services/`. `Program.cs` picks which implementation is constructed — don't hardwire a concrete service type into an endpoint file.
- **DTOs**: small immutable records where possible. Enums that need to serialize as strings (not ints) get an explicit `EnumXxxJsonConverter`, as with `EnumTargetCategoryJsonConverter`.
- **Dependency injection**: `PhotinoServer.CreateStaticFileServer(...)` already calls `WebApplicationBuilder.Build()` internally before returning the `WebApplication` — there's no hook to add registrations to *its* DI container (`app.Services` is sealed by the time we get `app`). So `Program.cs` builds a second, separate `ServiceCollection`/`ServiceProvider` (`Microsoft.Extensions.DependencyInjection` — the same library ASP.NET Core itself uses, just our own instance of it) purely for our own services: `ISettingRepository`, `IEncryptionSettingsService`, `IBrowserProfileService` are registered there as singletons, and each implementation's constructor dependencies (e.g. `StorageEncryptionSettingsService(ISettingRepository)`) are resolved by the container automatically. `Program.cs` still decides which implementation is registered for each interface (swap `StorageEncryptionSettingsService` for `MemoryEncryptionSettingsService` there, same as before — see the commented-out alternative). A new service should follow the same shape: interface + implementation, registered with `services.AddSingleton<IX, X>()`, then resolved once via `serviceProvider.GetRequiredService<IX>()` to pass into its `Map<Feature>Endpoints(...)` call — don't `new` a service directly in `Program.cs` any more.
- **Concurrency**: services doing file I/O guard state with `lock`. Since `SettingRepository` moved the settings-file I/O out of the services, each storage-backed service now only needs its own lock(s) for the in-memory cache it keeps (and, for `StorageEncryptionSettingsService`, a separate one for the actual encryption operation); `SettingRepository` keeps its own internal lock around the raw file read/write. Follow this pattern rather than introducing async/await plus separate concurrency primitives unless there's a real need.
- **Versioning & Releases**: Semantic Versioning (`MAJOR.MINOR.PATCH`), currently `1.0.0`. `Calypsov.csproj`'s `<Version>` property is the single source of truth — the .NET SDK derives `AssemblyVersion`/`FileVersion`/`InformationalVersion` from it automatically at build time, so nothing else needs hand-syncing. `IncludeSourceRevisionInInformationalVersion` is explicitly set to `false`, otherwise the SDK appends `+<git-commit-sha>` to `InformationalVersion` (the exact value `AppUpdateService.GetCurrentVersion()` reads and shows the user), which would make the displayed version ugly. `UserInterface/package.json`'s `version` field is deliberately left at its scaffold default — nothing in the app reads it, so tracking it separately would just be a second number to keep in sync for no benefit.
  - **Release recipe**: bump `<Version>` in `Calypsov.csproj` → run `scripts/package-macos.sh` (it now reads `VERSION` live via `dotnet msbuild Calypsov.csproj -getProperty:Version`, so it can never drift from the app's own reported version) → `git tag vX.Y.Z` → push the tag → create a GitHub Release from that tag with the built `.dmg` attached, **not** marked as a draft or a pre-release. GitHub's "latest release" API (`GET /repos/{owner}/{repo}/releases/latest`, used by `AppUpdateService`) deliberately excludes drafts and pre-releases — a release left as either one won't be detected by the in-app update checker.

- **Fix: logging stalled live encryption progress while a toggle was in flight.** `LogService.Enqueue()` originally called `_appSettings.GetIsRecordLogEnabled()` on every single `LogInfo`/`LogError` call — including from the new per-request middleware and from `EndpointHelpers.Try`'s exception logging — and that getter takes `StorageEncryptionSettingsService`'s own `_lock`. `ToggleEncryption()` holds that exact `_lock` for its *entire* zip/unzip run (by design, so the operation is atomic), so once logging was on, every `/api/*` request made during a toggle — including the frontend's `/api/encryption/progress` polls — blocked on that lock until the toggle finished, making progress look stuck until it suddenly jumped to 100%. Turn off the protection first before change any setting.")` — mapped to 409 by the existing `EndpointHelpers.Try` — whenever files are already encrypted or an encrypt/decrypt run is in progress. `ToggleEncryption()` itself is deliberately left unguarded, since turning protection *off* must always stay possible; the unused, unwired `SetEncryptionEnabled` wasn't touched either.
  - **Important ordering detail**: the "in progress" check (`EnsureNotCurrentlyToggling`, reading `GetProgress().IsRunning`) runs *before* `StorageEncryptionSettingsService` attempts to acquire its own `_lock` — not inside the `lock (_lock) { ... }` block. `ToggleEncryption()` holds that exact `_lock` for its *entire* zip/unzip run, so checking only after acquiring it would make a setting-change request silently block until the run finished (then succeed or fail based on the post-run state) instead of failing fast with a clear error. The separate "already encrypted" check (`EnsureNotEncrypted`) still runs inside the lock, against the already-loaded `AppSetting`, since that path never blocks for long. `MemoryEncryptionSettingsService` only needs the encrypted-check equivalent, since its `GetProgress()` is a stand-in that's always `IsRunning: false`.
  - Verified live without touching real data (the real `settings.json` currently has 0 targets): swapped in a disposable 3000-file dummy target, confirmed `POST /targets`, `PUT /zip-settings`, and `PUT /api/logs/setting` all return 409 with the exact message once encrypted; confirmed a setting-change request fired *while a real toggle was in flight* was rejected in ~13ms (not blocked until the toggle finished — the whole point of checking before the lock); confirmed all three succeed again once decrypted. Restored the real `settings.json` exactly afterward.
- **AppSetting encryption at rest (`IsEncryptAppSetting`)**: plaintext `settings.json` previously leaked exactly which folders/files were being protected to anyone who could just open the file — the thing being protected was listed in the open next to the un-protected data. `SettingRepository.Load<T>`/`Save<T>` now encode/decode transparently, so `IEncryptionSettingsService` (and anything else going through the repository) never has to know or care whether the file on disk is plain JSON or encoded:
  - **Write**: `Save<T>` checks `data is AppSetting { IsEncryptAppSetting: true }` — if so, the serialized JSON is Base64-encoded (`Convert.ToBase64String`) before being written; otherwise it's written as plain JSON exactly as before. Only `AppSetting` is ever encoded — `Save`'s generic contract for every other file type (e.g. `StorageBrowserProfileService`'s `browserProfiles.json`) is completely unchanged.
  - **Read**: `Load<T>`, when `T` is `AppSetting`, auto-detects the file's actual format (`raw.TrimStart().StartsWith('{')` → plain JSON; otherwise assumed Base64) and decodes before deserializing — regardless of the *current* `IsEncryptAppSetting` value, since that flag only controls the *next* write, not how an already-written file is read. This is what makes toggling the setting on/off, and reading a settings.json from before this feature existed, both just work with no migration step: an old plaintext file reads fine (and defaults `IsEncryptAppSetting` to `true` via the model's property initializer, so the very next save encodes it), and a file written while the flag was on still reads correctly even after the flag is later turned off.
  - New `GetIsEncryptAppSettingEnabled()`/`SetIsEncryptAppSettingEnabled(bool)` on `IEncryptionSettingsService` (implemented in both `StorageEncryptionSettingsService` and `MemoryEncryptionSettingsService`, the latter for interface parity only — it has no real file to encode), exposed as `GET`/`PUT /api/encryption/app-setting-encryption` in `EncryptionEndpoints.cs`. Follows the exact same "settings locked while protected" guard as every other AppSetting setter (`EnsureNotCurrentlyToggling()` before the lock, `EnsureNotEncrypted(appSetting)` inside it) — changing this flag while files are encrypted or a toggle is in progress is rejected the same way as changing targets or zip settings.
  - `AppSetting.IsEncryptAppSetting` defaults to `true` (the only AppSetting-backed bool that doesn't default to `false`), per the request that it be on by default for new and pre-existing installs alike.
  - Verified live, carefully, since the real `settings.json` had real data in it throughout this work (and its `IsEncrypted`/target-count state kept changing between checks — the real app was in concurrent use): confirmed the new code reads the real, already-existing plaintext file correctly (defaulting the new flag to `true`); confirmed the write-guard still rejects changes while protected. The full write-cycle (plain → encoded → plain → encoded again, each via a real API call, each verified against the raw file bytes) was otherwise tested against disposable dummy settings, including a cold backend restart to confirm an encoded file loads correctly from a fresh process, before restoring the real `settings.json` byte-for-byte from backup.
- **Clear a log file's content**: `ILogService.ClearLogFile(fileName)` (same filename validation as `GetLogFileContent`, extracted into a shared private `ValidateFileName`) empties the file via a new `ISettingRepository.WriteText(folderName, fileName, content)` — an overwrite counterpart to the existing append-only `AppendText`. The file itself is kept (still shows up in `GetLogFiles()`, with an updated modified time) — only its content is wiped, which is distinct from the retention logic's `DeleteFile` (which removes the file entirely). New `POST /api/logs/files/{fileName}/clear` in `LogEndpoints.cs`, 204 on success.

  - **Caused real data loss while testing, worth recording**: the pre-existing 4-file retention policy (`LogService.EnforceRetention`) deletes the oldest log file whenever more than 4 exist, and runs on every scheduler tick while `IsRecordLog` is on. Creating several disposable test log files during this verification, without accounting for that cap, pushed the real file count over 4 while the real scheduler was active — it correctly (if unintentionally, from the testing process's perspective) deleted the real, oldest `2026-10-10.log`. Not a bug in this feature or in retention itself — both worked exactly as designed — but a process mistake: future testing that adds extra log files to the real Logs folder should either use dates old enough to be deleted first, or keep the real file count at or under 4 throughout.
