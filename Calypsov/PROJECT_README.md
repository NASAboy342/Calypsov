# Backend Project Doc (Calypsov)

Maintained by the `back-end-enhance` skill. Read this before planning any backend change; update the Feature log after implementing one. This is a living architecture/convention doc, separate from `ReadMe.md` (which only covers build/run setup).

## Stack
- .NET 8, C#, `OutputType: Exe` — this runs as a native apphost (`bin/Debug/net8.0/Calypsov`), not `dotnet Calypsov.dll`.
- Photino.NET + Photino.NET.Server — hosts an ASP.NET minimal-API backend and a native OS window in one process.
- Newtonsoft.Json for settings persistence (`JsonConvert`); minimal-API results elsewhere use `Results.*`.
- Two run modes wired in `Program.cs` via `Program.IsDebugMode` (`#if DEBUG`):
  - Debug: window loads `http://localhost:5173` (the Vite dev server — see the `run-test` skill).
  - Release: window loads the built `wwwroot` bundle (embedded via `Resources/wwwroot`), with a cache-busting query string on load.

## Structure
- `Program.cs` — composition root. Creates the Photino static file server, builds a `ServiceCollection`/`ServiceProvider` to register and resolve services (see **Dependency injection** below), calls each feature's `Map<Feature>Endpoints(...)` extension method, then creates and shows the `PhotinoWindow`.
- `Api/` — one static class per feature (e.g. `EncryptionEndpoints.cs`, `DialogEndpoints.cs`). Each exposes a single `Map<Feature>Endpoints(this WebApplication app, ...)` extension method that groups its routes under `/api/<feature>` via `app.MapGroup(...)`.
- `Services/` — one interface per feature (`I<Feature>Service`) plus one or more implementations (e.g. `StorageEncryptionSettingsService` persists to a JSON file under the OS app-data folder; `MemoryEncryptionSettingsService` is an in-memory stand-in). `Program.cs` is the only place that decides which implementation is live — swapping implementations never touches the API surface. Services can depend on other services' interfaces this same way — `StorageEncryptionSettingsService` now also takes an `IBrowserProfileService` (see Feature log) — and the DI container resolves the whole graph automatically; nothing in `Program.cs` had to change to wire that up.
- `Repositories/` — `ISettingRepository`/`SettingRepository`: shared by every storage-backed service (currently `StorageEncryptionSettingsService`, `StorageBrowserProfileService`) to read/write a JSON settings file and to resolve the app-data folder, so each service only names its own file (`Load<T>("x.json")`/`Save("x.json", data)`) instead of re-resolving where "the app's folder" is. One instance is constructed in `Program.cs` and passed into every service that needs it (constructor injection).
- `Models/` — plain C# records/classes: response DTOs (`EncryptionStatusResponse`, `PickPathsResponse`, `ErrorResponse`), request DTOs (`AddTargetRequest`), domain types (`EncryptionTarget`, `AppSetting`, `EnumTargetCategory` + its JSON converter).
- `Helpers/` — small stateless utilities used by services (e.g. `Zip.cs` zips/unzips target folders and files).

## Conventions
- **Endpoint pattern**: `app.MapGroup("/api/<feature>")`, then `MapGet/MapPost/MapDelete` with lambda bodies. Bodies that can fail are wrapped in a local `Try(Func<IResult> body)` helper (see `EncryptionEndpoints.cs`), which turns `ArgumentException` → 400, `InvalidOperationException` → 409, anything else → 500, all as a JSON `ErrorResponse { message }`. Keep new endpoint files consistent with this — the frontend's `httpClient.requestJson` reads `body.message` on any non-2xx response, so an endpoint that doesn't follow this shape breaks that error handling.
- **Service pattern**: define the interface first, with XML doc comments explaining what each thrown exception means (since `Try` maps them to status codes). Put implementation(s) in `Services/`. `Program.cs` picks which implementation is constructed — don't hardwire a concrete service type into an endpoint file.
- **DTOs**: small immutable records where possible. Enums that need to serialize as strings (not ints) get an explicit `EnumXxxJsonConverter`, as with `EnumTargetCategoryJsonConverter`.
- **Dependency injection**: `PhotinoServer.CreateStaticFileServer(...)` already calls `WebApplicationBuilder.Build()` internally before returning the `WebApplication` — there's no hook to add registrations to *its* DI container (`app.Services` is sealed by the time we get `app`). So `Program.cs` builds a second, separate `ServiceCollection`/`ServiceProvider` (`Microsoft.Extensions.DependencyInjection` — the same library ASP.NET Core itself uses, just our own instance of it) purely for our own services: `ISettingRepository`, `IEncryptionSettingsService`, `IBrowserProfileService` are registered there as singletons, and each implementation's constructor dependencies (e.g. `StorageEncryptionSettingsService(ISettingRepository)`) are resolved by the container automatically. `Program.cs` still decides which implementation is registered for each interface (swap `StorageEncryptionSettingsService` for `MemoryEncryptionSettingsService` there, same as before — see the commented-out alternative). A new service should follow the same shape: interface + implementation, registered with `services.AddSingleton<IX, X>()`, then resolved once via `serviceProvider.GetRequiredService<IX>()` to pass into its `Map<Feature>Endpoints(...)` call — don't `new` a service directly in `Program.cs` any more.
- **Concurrency**: services doing file I/O guard state with `lock`. Since `SettingRepository` moved the settings-file I/O out of the services, each storage-backed service now only needs its own lock(s) for the in-memory cache it keeps (and, for `StorageEncryptionSettingsService`, a separate one for the actual encryption operation); `SettingRepository` keeps its own internal lock around the raw file read/write. Follow this pattern rather than introducing async/await plus separate concurrency primitives unless there's a real need.

## Feature log
- *(baseline)* Encryption on/off + target folder/file management (`EncryptionEndpoints`, `IEncryptionSettingsService`, `StorageEncryptionSettingsService`), backed by zipping targets and deleting originals (reversed on toggle-off). Native file/folder picker dialogs (`DialogEndpoints`).
- Browser profile selection for Edge/Chrome (`BrowserEndpoints`, `IBrowserProfileService`, `StorageBrowserProfileService`): `GET/POST /api/browsers/{browser}/selection` persist which profile id is picked per browser (`browserProfiles.json`, default `null` = "None") — fully implemented.
  - `GetMsEdgeBrowserProfiles()` is now implemented: reads Edge's `Local State` file (`profile.info_cache`) for each profile's folder name + display name, and — if the profile has a cached account picture (`Google Profile Picture.png` / `Edge Profile Picture.png` in the profile's own folder) — inlines it as a base64 `data:` URI in `AvatarUrl` so the frontend needs no extra endpoint to serve it. `GetEdgeUserDataDirectory()` covers Windows/macOS/Linux paths. `BrowserProfile` gained a `folderPath` field (the profile's absolute folder path) for anything that needs to read more from the profile later. Note: a full-resolution cached picture can be several hundred KB as base64 — fine for a local single-user settings page, but worth downsizing the image before encoding if this ever needs to scale to many profiles.
  - `GetDisplayName()` (used by `GetMsEdgeBrowserProfiles`): prefers the signed-in account's email (`user_name` in `info_cache`) over Edge's own generic `name` field ("Profile 1"/"Profile 2"/…), since the generic name doesn't tell a user which account a profile actually is — and two profiles signed into different accounts can even share the same real name, so email is what actually disambiguates them. Falls back to the generic name for a profile that isn't signed into any account.
  - `GetChromeBrowserProfiles()` is now implemented the same way, reusing the shared logic: since Edge and Chrome are both Chromium-based with an identical `Local State`/profile-folder layout, the profile-reading body was extracted into `GetChromiumBrowserProfiles(userDataDirectory)`, called by both `GetMsEdgeBrowserProfiles()` (→ `GetEdgeUserDataDirectory()`) and `GetChromeBrowserProfiles()` (→ new `GetChromeUserDataDirectory()`, covering Windows/macOS/Linux paths). No more browser-detection stubs remain.
- Extracted `Repositories/ISettingRepository` + `SettingRepository` from the app-data-folder resolution that used to be copy-pasted, line for line, in both `StorageEncryptionSettingsService.GetSettingPath()` and `StorageBrowserProfileService.GetSettingPath()` (kept the `StorageEncryptionSettingsService` version as the canonical one, since they were identical). The repository now owns both the folder resolution (`GetAppDataFolder()` — also used by `StorageEncryptionSettingsService.GetEncrypFolderPath()` for the "Encryption" zip-storage subfolder, not just the settings file) and the generic JSON load/save (`Load<T>(fileName)`/`Save(fileName, data)`) each service used to hand-roll around it. Both services now take an `ISettingRepository` via constructor injection; `Program.cs` constructs one shared instance and passes it to both. Verified no behavior change: encryption status/targets add-remove and browser profile list/selection round-trips all still read/write the same `settings.json`/`browserProfiles.json` files as before.
- Switched `Program.cs` from manually `new`-ing up `ISettingRepository`/`IEncryptionSettingsService`/`IBrowserProfileService` to registering them in a real DI container (`ServiceCollection` + `services.AddSingleton<TInterface, TImpl>()`, resolved via `serviceProvider.GetRequiredService<TInterface>()`) — see the new **Dependency injection** convention above for why it's a separate container rather than `builder.Services`. Verified no behavior change: full re-test of encryption add/list/remove-target and the browser-profile list/selection round-trip, including against the real, pre-existing `settings.json` data on this machine.
- Wired the selected browser profile(s) into what gets encrypted: added `IBrowserProfileService.GetSelectedProfile()` (`StorageBrowserProfileService`) which, for each browser with a non-`null` selection, looks up the matching `BrowserProfile` from `GetProfiles(browser)` and returns a `Dictionary<BrowserType, BrowserProfile>` of just the browsers that actually have one selected. `StorageEncryptionSettingsService` now takes `IBrowserProfileService` as a second constructor dependency (DI resolves it automatically, no `Program.cs` change needed) and calls it from the new `AddBrowserProfileFolderToFolderToEncryp()`, which adds each selected profile's `folderPath` to the list of folders `EncrypFolders()` zips up — so toggling encryption on now also sweeps up whichever browser profile folders are selected in Settings, not just the manually-added folder/file targets.
  - `EncrypBrowserProfiles()`/`DecrypBrowserProfiles()` (called from `ProcessEncryption`/`ProcessDecryption`) are still empty stub hooks — nothing to do yet, left for whatever browser-profile-specific encryption behavior (beyond just zipping the folder alongside the other targets) turns out to be needed.
  - Known nit, not yet fixed: `BrowserProfile.folderPath` is lowercase, inconsistent with the record's other PascalCase properties (`Id`, `Name`, `AvatarUrl`) — flagged once already, still there.
- Real (not simulated) progress reporting for the encrypt/decrypt toggle: `GET /api/encryption/progress` → `EncryptionProgress { IsRunning, Completed, Total, CurrentItem }`, added to `EncryptionEndpoints.cs`'s existing group. `POST /api/encryption/toggle` still blocks exactly as before (no change to its contract) — the frontend polls `/progress` concurrently on a separate request while `/toggle`'s POST is in flight, which works because Kestrel serves concurrent requests fine even while one handler is a long synchronous call; there was no need to make `ToggleEncryption()` itself async/background.
  - `StorageEncryptionSettingsService` computes the grand total up front — for encrypt: existing-file count + every folder target's (and every selected browser profile folder's) recursive file count; for decrypt: `Zip.CountManifestEntries(zipPath)` (new `Zip.cs` helper — peeks `manifest.json`'s file count without extracting) summed across `CalypsovFiles.zip`/`CalypsovFolders.zip` — then threads one running `completed` counter through both phases (files, then folders) via a callback, so the bar climbs continuously across the whole operation instead of resetting per phase.
  - `Zip.ZipFiles`/`ZipFolders`/`UnzipFile` all gained an optional `Action<string>? onFileProcessed` parameter, invoked once per individual file with its real filesystem path — that's `CurrentItem`, so the UI message names an actual file, not just "processing...".
  - **Locking**: progress is guarded by its own new `_lockProgress`, deliberately separate from `_lock` — `_lock` is held for `ToggleEncryption()`'s *entire* duration, so if `GetProgress()` shared it, every poll would block until the whole run finished, defeating the purpose. `_lockProgress` is only ever held briefly, to read or replace the `EncryptionProgress` snapshot.
  - `IsRunning` is always reset to `false` in a `finally` around both `ProcessEncryption()`/`ProcessDecryption()`, so a mid-run exception (e.g. the existing Full Disk Access errors) can't leave progress stuck reporting `isRunning:true` forever.
  - Verified live: added a real target, ran the actual toggle in the background while polling `/progress` concurrently — watched `completed`/`total`/`currentItem` advance in real time through real file paths, then flip to `isRunning:false` in sync with the `/toggle` POST completing. Verified symmetrically for decrypt (files were actually restored to disk).
- Added storage + API for two new zip settings the frontend's new "Encryption Options" section needs: `IsUseTurboZip` and `IsEncryptZippedFile` (two new `bool` fields on `AppSetting`, defaulting `false`). Followed the existing `IsEncrypted` shape exactly: new `Models/ZipSettings.cs` (`ZipSettings(bool IsUseTurboZip, bool IsEncryptZippedFile)`, serializes camelCase automatically like every other record here) and `Models/UpdateZipSettingsRequest.cs`; `IEncryptionSettingsService` gained `GetZipSettings()`/`SetZipSettings(bool, bool)`, implemented in both `StorageEncryptionSettingsService` (under the existing `_lock`, read/write through `GetAppSetting()`/`SaveAppSetting()`) and `MemoryEncryptionSettingsService` (new `"encryption:zipSettings"` cache key); `EncryptionEndpoints.cs` gained `GET`/`PUT /api/encryption/zip-settings` in the existing `/api/encryption` group, wrapped in the same `Try(...)` helper. Verified live: `GET` before/after a `PUT` round-trips correctly and survives a backend restart (real `settings.json` persistence), then reset to `false`/`false` to leave the developer machine's real settings untouched.
  - **Deliberately left unimplemented**: nothing in `Helpers/Zip.cs` or the encrypt/decrypt pipeline reads these two flags yet — they're stored and returned, nothing more. Turning `IsUseTurboZip` into real behavior needs a thread-safe redesign of `Zip.ZipFolders`/`ZipFiles` (currently one `ZipArchive` written to sequentially — not safely parallelizable as-is). Turning `IsEncryptZippedFile` into real behavior needs the user to decide a key-management approach first (e.g. a user-supplied passphrase vs. an app-derived key) before any crypto code is written, since guessing wrong here would bake in a security design nobody signed off on.
- **Turbo Zip, v1** (`IsUseTurboZip` now actually does something): per the user's own proposed design, `Helpers/Zip.cs` is still untouched — "parallel" means zipping folders into *multiple numbered archives* instead of parallelizing writes to one `ZipArchive` (which isn't safe). In `StorageEncryptionSettingsService.EncrypFolders()`, a new `ShouldUseTurboZip(folderCount)` gate (`appSetting.IsUseTurboZip && folderCount > TurboZipFolderThreshold`, threshold = 20, matching the user's original spec) branches to the new `ZipFoldersInParallel()` instead of the old single-call `Zip.ZipFolders(...)`:
  - `ChunkEvenly()` round-robins the folder list into `Math.Min(Environment.ProcessorCount, folders.Count)` chunks (so a chunk is never empty), and `Parallel.For` runs one `Zip.ZipFolders(chunk, ...)` per chunk — each writes to its *own* `ZipArchive` instance (`GetTurboZipPartFileName()`: `CalypsovFolders.zip` → `CalypsovFolders.part1.zip`, `.part2.zip`, …), so there's no shared-archive thread-safety concern. `AggregateException` from `Parallel.For` is unwrapped in a catch so callers still see the same exception types (`UnauthorizedAccessException`, etc.) as the single-threaded path.
  - **Decrypt side**: new `GetEncryptedFolderZipPaths()` looks for the single `CalypsovFolders.zip` first (non-Turbo run), falling back to `CalypsovFolders.part*.zip` (sorted in human numeric order via `GetTurboZipPartIndex`, so `part2` sorts before `part10`) if that's what's on disk instead — the two forms never coexist for the same run. `DecrypFolders()`, `CleanupEncryptedFolderFile()`, and `ProcessDecryption()`'s total-file count (`GetEncryptedFolderZipPaths().Sum(Zip.CountManifestEntries)`) all go through this one helper now, so they automatically handle either form. Unzipping the parts is still sequential in this v1 (the user only asked for parallel *progress*, not parallel *unzip* — a reasonable place to stop for a first version).
  - **Per-thread progress**: `EncryptionProgress` gained a `Threads: IReadOnlyList<ZipThreadProgress>` field (new `Models/ZipThreadProgress.cs`: `ThreadIndex, Completed, Total, CurrentItem`) — empty unless Turbo Zip actually kicked in. A new `ConcurrentDictionary<int, ZipThreadProgress> _threadProgress` field holds each worker's latest snapshot (`ReportThreadProgress()`, called from each `Parallel.For` worker's own `onFileProcessed` callback with its own chunk's running count); `SetProgress()` snapshots it (sorted by `ThreadIndex`) into every `EncryptionProgress` it builds, and `ClearThreadProgress()` resets it at the start/end of both `ProcessEncryption()` and `ProcessDecryption()`. The pre-existing overall `completed` counter in `ProcessEncryption()` switched from a plain `completed++` to `Interlocked.Increment(ref completed)`, since multiple Turbo Zip workers can now report a finished file at the same instant.
  - Files (zipped via `EncrypFiles`) are **not** Turbo-Zip'd in this v1 — the user's own spec was folder-count-specific ("if the target folder is more than 20"), so this was left as the existing single-archive path. Extending the same `ShouldUseTurboZip`/`ZipFoldersInParallel` pattern to files later would be a small, analogous follow-up if wanted.
  - Frontend: `services/encryptionApi.ts`'s `EncryptionProgress` gained `threads: ZipThreadProgress[]`; `EncryptionProgressBar.vue` renders one thin sub-bar per thread (teal, under the main amber bar) whenever `threads.length > 0`, each with its own live percentage — this is what makes the "parallel progress bar" visible, not just plumbed.
  - **Verified correctness in an isolated sandbox, not against real data**: the real `settings.json` on this machine has the user's actual 32 real target folders, and `ToggleEncryption()` *deletes the originals* after zipping them (existing behavior, unchanged) — so exercising a real toggle in dev would have destroyed real folders. Instead, built a disposable throwaway console harness (outside the repo, deleted after the run) that referenced this project's real classes with fake `ISettingRepository`/`IBrowserProfileService` pointed at a temp directory, created 30 dummy folders (90 dummy files) with `IsUseTurboZip` on, and ran the real `ToggleEncryption()` both ways. Confirmed: on an 11-core machine, exactly 11 `CalypsovFolders.partN.zip` files were created with correct per-part file counts (e.g. 8 threads @ 9 files, 3 threads @ 6 files = 90 total, matching 30 folders × 3 files); the per-thread progress snapshots reported correctly during the run; all 30 dummy folders were restored with byte-for-byte correct content on decrypt; and the Encryption folder was empty afterward (no leftover parts). The temp sandbox was deleted at the end regardless of outcome.
